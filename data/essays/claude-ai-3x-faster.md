# 我们如何在两周内把 claude.ai 提速约 3 倍

作者：Raymond Wang、Sam Attard、Issac G.
发布：2026-09-23
来源：https://claude.dev/blog/how-we-made-claude-ai-faster/

Claude 一旦能量到某个东西，就能把它做快。于是我们不停地找更多可以量的东西。

今年八月，我们用两周冲刺，把 claude.ai 和 Claude 桌面端的核心用户体验大约提速了 3 倍。用户一直在说它慢，他们说得对。整场冲刺都从同一个 Slack 频道里推进，每个线程里都有 Claude。

我们聚焦占用户活动约 95% 的四条路径。在第 75 百分位上：冷启动打开 claude.ai 到出现可打字页面，从 3.1 秒降到 0.55 秒；新开 Claude Code 会话从 0.8 秒降到 0.3 秒；加载 Claude Cowork 云端会话从 2.6 秒降到 0.73 秒。合计估算，每天能少让用户空等成千上万小时。

我们使用的是 Claude Tag（beta），背后跑的是一支内部研究模型，能力大致对标 Opus 5.5。Claude 找瓶颈、搭基准、推改进，并盯着每一次部署。我们这边定目标、做取舍、审批每一处改动。靠这套做法，合并了三千多项改动，没有一次面向客户的事故，也没有回滚。下文讲我们交付了什么、怎么度量，以及和 Claude 一起安全推进的回路。

## 简报

冲刺开始前，我们建了一个 Slack 频道，并立下如下常驻指令：

> @Claude 你的工作是推动一切与 claude.ai 网站和桌面端性能相关的事务。你的职责包括：监控部署是否出现性能回归、评估现有遥测的准确性与完备性、维护整理良好的可观测性看板、主动为已观察到的问题与低垂果实落地解决方案、提出性能相关项目机会，并与人类队友沟通。[…]
>
> 这个频道的终极目标是让你尽可能自主，但今天我们知道那还做不到。

我们让 Claude 通过 Datadog MCP 服务器分析用量数据。它锁定了四条影响最大的用户路径：启动应用、开启对话、加载已有对话、发送消息。覆盖网页与桌面端、以及我们各产品之后，这些路径一共对应十三项独立指标。为了建立基线，我们持续加装埋点，直到它们可以直接比较：每一项都以一次用户交互开始，到结果渲染完成结束，并分清客户端工作与服务端工作。

冲刺以大约二十个精选项目开场，每个项目针对一条具体路径。Claude 估算每个项目能省多少毫秒，我们把这些估算汇总起来，定下冲刺目标。其中一些项目相当大，但我们认为两周内大概能完成大部分。

到第三天，十三项目标里我们已经打中了十二项。

计划内的项目很早就落地。为了更快启动：我们把一份静态 composer 烤进 HTML，让用户在 React 初始化期间就能打字；并为桌面壳的主进程预编译 V8 代码缓存，这样就不用每次从零重新编译。为了更快导航：会话之间保持 composer 挂载、用户悬停时预取会话，并把侧边栏重渲染砍掉了 90%。

我们也给 Claude 留了空间去发现机会、提出新的工作流。那些工作流很快各自长成完整项目，远远超出了我们最初的目标。于是我们定下新目标，再去找更多可以量的东西：

> @Claude 我们几乎把最初项目列表里的每一项都资助了，而且还不止那些。来刷新一轮吧 […] 还有什么我们没探索过？还能在哪些地方继续爬山优化？眼下最大的机会在哪里？[…] 我愿意听 WACKY（怪）点子

## 什么都能爬山优化

从一开始我们就知道，自己想要比部署节奏更快地迭代。Claude 可以异步工作许多小时，甚至整夜；我们希望让它在不等待线上读数的情况下验证原型。为此，我们寻找在实验室里度量性能的其他办法。

Sam 找到第一条线索：不要只看墙钟时间，去量 JS 指令数。对纯 JS 热路径：用 Valgrind 配合 `node --predictable`，再与入库的基线对比——跑一次就够，不需要统计。对浏览器路径：每次交互的 React commit 次数、V8 精确覆盖率给出的函数调用次数、layout 与 style-recalc 次数、DOM 变更次数。

十一分钟后，五个线程在不同度量上跑了起来。

我们对每一项新基准都抱着怀疑态度。每一项都有两项任务：第一，给 Claude 一个能在实验室里推动的指标；第二，在 CI 里装上一道护栏，数字只能单向收紧。如果基准飘忽不定，或者与用户延迟并不真正相关，我们就扔掉它。

墙钟时间才是用户的体感，但噪声大。指令数是确定性的，但我们仍需要 Claude 证明它们与墙钟时间一致。于是我们让 Claude 把两条热路径上的指令数压下去：组装一段对话的消息树，以及扫描 Claude Code 输出里状态行的扫描器。Claude 用 Valgrind 给两边都做了剖析，发现第一条路径里有四分之一的指令花在多态字典查找上——同一个消息 ID 被解析了三次。

一小时后，两条路径上的指令数分别砍掉了 48% 和 31%，墙钟时间分别下降了 78% 和 44%。我们入库了两道新的单向收紧护栏。从那以后，任何把这些路径指令数抬高的 PR 都会让 CI 失败；每天还有一个任务，只要计数下降就把上限再往下调。

这引出了整场冲刺的核心教训。有了 Claude，能量到的东西就变得可攻。测量曾经是第零步；有了 Claude，它是爬山的第一步。一旦 Claude 有了一个要打败的数字，它就能开始优化。我们能做的杠杆最高的事，就是再找更多可以量的东西。

## 回路：一个线程一个线程来

这一切都发生在同一个 Slack 频道里。冲刺渐渐固定成这样一套回路：

1. 有人开一个线程，讨论某条路径里一段偏慢的地方，常常附上截图或录屏。
2. Claude 追链路，然后找到或搭好一个能把问题演示出来的基准。
3. 一旦实验室里有了像样的结果，Claude 就会带着 PR 回来——常常是好几个，按风险与可审阅粒度切分，凡是用户可见的改动都藏在开关后面。
4. 上线之后，Claude 盯着部署，并读取线上数据。
5. 如果性能改善了，Claude 就通过收紧基准把成果锁住；如果没有，它关掉开关继续迭代。
6. 然后它在同一条路径上寻找下一个慢点。

举个例子：页面加载之后，侧边栏的行才「蹦」出来。Chat 与 Cowork 的行在不同时间解析完成。Cumulative Layout Shift 分数大约是 0.008——远低于「良好」阈值 0.1。Issac 建议使用 Layout Instability API。Claude 创建了一个遥测事件，把每次 `layout-shift` 的 `sources` 映射到具名区域（sidebar、transcript）以及阶段（首次绘制前、可打字之后）。它还加了一套集成测试：故意把侧边栏数据拖到首次绘制之后才给出，并在任何具名区域出现任何位移时失败。这个测试在 main 上 20/20 红，在 PR 上 20/20 绿。

事件上线后，Claude 发现：31% 的网页加载在页面已经可用之后、且没有任何用户交互的情况下，仍然移动了某些东西。Claude 按名字逐个排查原因：晚出现的表头行、用户名加载时光标滑动、滚动条出现时列表整体挪动。它先把最严重的几处成批修掉，然后再找下一批。

冲刺期间，我们同时跑过一百五十多个线程。

## 横向扩展

一旦回路在一个线程上跑通，要在更多线程上跑，只需要把它们打开。原始请求做完之后 Claude 并不关线程，而是继续干。单个线程常常能堆出五十个、有时一百个优化 PR。越来越多是 Claude 自己、而不是人类，在开新线程。Shelley 观察到：「[这个模型] 是个数字恶魔。」

每量到一处，就能找到可改进的东西。Claude 做了一次 React hook 普查，发现 composer 打字路径上有 6,900 个 hooks 和 900 个 store 订阅，每一次按键都会重渲染。单独一个 `:root:has()` 选择器，给每一次 DOM 变更多加了 24 毫秒。残留的 `location.reload()` 每天造成约五十万次隐蔽的整页刷新。空闲标签页每分钟两次在主线程上，把相同的缓存快照克隆进 IndexedDB。

在一次针对 CPU 卡顿的排查中，Claude 注意到：高亮一个已完成的代码块，可能让页面冻结大约一秒。罪魁祸首：长破折号（em dashes）。非 Latin-1 字符迫使 V8 把整段字符串存成 UTF-16，于是每一个语法高亮正则都走上更慢的双字节路径。修复只需二十行改动：在高亮前，把每个代码块拷贝成单字节字符串。

到第二周，最忙的几天一天会落地两百多处改动。大约三分之一的 PR 里还附带了额外的遥测或护栏。在同一个频道里工作，意味着一切都公开发生。其他团队也会把改动带进这个频道做性能评审。

## 护栏

因为几乎碰到的都是热路径，安全从一开始就摆在前面：自动审查，且至少一名人类批准；优化前先写单元测试；用户可见的问题藏在短生命周期的功能开关后面。大约上了近两百个开关；冲刺结束前，超过一半已经清理掉。

性能收益会衰减。一旦某个项目证明了收益，就要保护它。静态 composer 几乎立刻给用户展示一份 HTML 副本，再由 React 画在上面。如果 React 偏了一个像素，魔术就破了。Claude 建了几十道护栏：用 jsdom 渲染真实 React 组件来生成静态标记，并配漂移测试；跨十四种视口尺寸的集成套件，断言对齐误差在 1 px 以内；贯穿交接过程的按键测试；以及把位移上报到十分之一像素精度的线上报告。

高风险改动先对公司员工放量，再放到百分之一用户，最后全量。静态 composer 对内发布四小时后，一位同事看到：在新标签页打开 claude.ai 时，大约出现 15–20px 的垂直布局位移。Claude 追到根因：Chrome 在地址栏投机预渲染之后，会把一个 56 px 的托管浏览器页脚缩掉——问题不在静态到 React 的交接。Claude 在这次尺寸变化中把布局钉住，并加了一个预渲染模拟测试。

## 掌舵

这套回路并不是完全自主的。人类有三份工作：

野心。Claude 默认很谨慎。Raymond：「请更大胆一点。」目标打中之后，Sam 一个线程一个线程地催：目标不是停下来的地方。

品味。每个线程指定一位具名人类负责人。Claude 会把用户可感知的改动用前后对比标出来，交给人类裁决——例如按单元格填表 vs 等整行就绪、骨架屏时机、逐字淡入的代价。

方向。线程刻意收窄。排好先后顺序，看清用户影响。有一个 900 行的 PR 收到的回复是：「我要敲槌裁定：每次发送省 2ms，不值得为它维护这个构建插件的复杂度。」

## 8 毫秒预算

Claude 演示过一次实时语法高亮的正则优化，并带上帧率读数。Raymond 要求把它推到 120 fps / 8.3 ms 的帧预算。Claude 通过 DevTools 的 begin-frame 控制，在无头 Chrome 里搭起了确定性的 120 Hz 逐帧步进。

Claude 通过对已完成块做记忆化，消除了每个 chunk 上 O(消息长度) 的工作；把不断增长的代码围栏的分词挪到 worker；并按单元格逐格揭示表格。那个线程里差不多有六十个 PR。长回复对主线程的总阻塞从大约 750 ms 降到大约 200 ms，CPU 大约只用到原来的三分之一，并在一台 120 Hz 的 MacBook 上从头到尾稳住 120 fps。这套 120 Hz 装置后来变成了夜间定时任务。

## 接下来

今天，claude.ai 和桌面端相对八月初大约快了 3 倍，而这些单向收紧的护栏应该能把成果守住。第 95 百分位、其他路径，以及很长的对话，仍有空间。另文会写：在 Electron、Chromium、Node.js 等上游里的支线任务。这个频道还在继续跑。
